# 版本流程：每个版本要经过的完整流程

> 版本号采用语义化版本 `主版本.次版本.修订号`（如 1.0.0 / 1.1.0 / 1.0.1）。每个版本 — 不分大小 — 都走完下列流程，区别只在每步的深度（见第三节）。任何一步未过，不许进入下一步；跳步视为流程事故，记录在案。
>
> **这十步是一个循环，不是一条直线**（2026-11-17 发起人定）：第 10 步的产出直接回到第 1 步，开启下一个版本。产品只要还在被使用，循环就不停 — 使用者不断使用、不断提出新意见，我们不断修改、不断发新版本。循环的终止条件只有一个：产品正式退役（由发起人决定并归档）。

## 一、标准流程（十步）

| 步 | 阶段 | 负责组 | 做什么 | 产出物 | 过关条件 |
|---|---|---|---|---|---|
| 1 | 需求池与立项 | 需求组 + 产品/项目组 | 从需求池（用户反馈、缺陷、规划）筛选本版范围，写版本目标（一句话）与不做清单 | 版本立项单 | 发起人确认范围 |
| 2 | 需求细化与评审 | 需求组 | 入选需求细化到 REQUIREMENTS 同等颗粒度（编号、规则、验收标准）；客户代表做价值评审，用户研究组做场景走查 | 更新后的需求文档 + 两份视角评审 | 评审通过，发起人确认 |
| 3 | 设计 | 设计组 + UI 组 | 交互稿与视觉稿覆盖新增/变更页面与全部状态（空/加载/错误/离线）；架构组同步评估影响面 | 设计稿 + 架构影响说明 | 设计评审通过（UI 组走查标准见 DESIGN.md） |
| 4 | 详细设计 | 架构组 + 开发组 | 协议/数据表/接口变更写成详细设计；测试组同步把验收标准转成测试用例 | 详细设计文档 + 测试用例集 | 详设评审通过；用例覆盖每条验收标准 |
| 5 | 开发 | 开发组 | 按模块实现，自带单元测试；注释全中文；每日构建保持可运行 | 代码 + 单测 | CI 三平台全绿（构建+单测+clippy） |
| 6 | 代码评审 | 开发组（交叉评审） | 交叉评审全部合入代码，重点看分层违规、错误处理、热路径性能 | 评审记录 | 无未解决的阻塞级意见 |
| 7 | 提测与测试 | 测试组 | 按用例执行功能测试；专项：三平台兼容、传输压力（大文件/弱连接）、长会话性能、安全抽查 | 测试报告 + 缺陷单 | 无高优先级缺陷未关闭；中低缺陷有明确处理结论 |
| 8 | 用户验收（UAT） | 用户研究组 + 客户代表 | 按三类画像的典型场景做验收测试；客户代表核对客户验收单 | UAT 结论 + 客户验收单 | 两方签字通过（记录），问题回流第 2/5 步 |
| 9 | 发布 | 发布组 | 打预览版（preview 标签）→ 观察至少一轮反馈 → 打正式版：三平台安装包、发布说明（新功能/修复/已知问题）、版本号与标签对齐 | 安装包 + 发布说明 | 发起人最终确认后才对外发布 |
| 10 | 复盘与回流 | 产品/项目组 | 上线反馈与缺陷统计、流程问题复盘；新需求与遗留问题回流需求池，成为下一版本输入 | 版本复盘记录 | 复盘记录归档，需求池更新 |

## 二、循环机制：反馈如何驱动下一圈

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
  ①需求池立项 → ②需求评审 → ③设计 → ④详设 → ⑤开发        │
        → ⑥代码评审 → ⑦测试 → ⑧UAT/客户验收 → ⑨发布 ──┤
        → ⑩复盘回流 ────────────────────────────────────┘
                     ▲
        使用者持续使用中的反馈（随时，不等版本结束）
```

三条回流通道，时刻开启：

1. **版本内回流**：任一关口被打回（评审不过、测试失败、UAT 不通过、发起人提出修改），退回对应的上游步骤修改，改完重新过关 — 本项目需求、组织、设计三稿的返工就是这条通道的实例。
2. **版本间回流（主循环）**：第 10 步复盘把上线反馈、缺陷统计、新意见全部写入需求池，成为下一版本第 1 步的输入；需求池按价值与紧急度排序，滚动更新，永不清空到零为止才开新版 — 有积压就持续迭代。
3. **使用中直达反馈**：使用者在日常使用中提出的意见（包括发起人本人在使用中发现的问题），由需求组随时登记进需求池并打标（缺陷/体验/新功能）；严重缺陷不等下一版本，直接触发紧急修复流程（第四节 hotfix）插入当前循环。

每圈循环的节奏：一个版本一圈；圈与圈之间不设"项目结束"，只设版本归档。流程文档本身也在循环内 — 每圈复盘时若发现流程不合用，按变更记录修订本文件。

## 三、分支与状态规则

- 主干 `main` 永远可构建、可发布；版本开发在 `release/x.y` 分支上收敛，修复只进该分支与主干，不另开长期分支。
- 版本状态机：规划中 → 开发中 → 测试中 → 验收中 → 已发布 → 已归档。状态只向前走；验收或测试打回时回退到开发中并留痕。
- 每个版本在仓库打同名标签（如 `v1.1.0`），与安装包内版本号、发布说明三者必须一致，对不上不许发布。

## 四、按版本类型的深度差异

| 类型 | 例 | 流程差异 |
|---|---|---|
| 大版本（主版本 +1） | 1.0.0 首发、2.0.0 | 十步全走满；设计与详设做完整评审；UAT 覆盖全部画像场景 |
| 功能版本（次版本 +1） | 1.1.0 加命令面板 | 十步全走；设计/详设只覆盖增量部分，但评审与关口不减 |
| 修订版本（修订号 +1） | 1.0.1 修缺陷 | 第 2、3 步可合并为缺陷单评审（需求组确认影响面）；其余步骤不减，测试须含回归 |
| 紧急修复（hotfix） | 正式版严重缺陷 | 可先行开发与发布预览，但 72 小时内补齐全部文档与评审记录；发起人事后确认 |

## 五、红线

- 没有测试报告的版本不发布；没有客户验收单的版本不发布；CI 红灯不合入、不提测。
- 发布说明必须写已知问题，不许藏缺陷。
- 任何一步的"通过"都要有产出物为据（文档、报告、记录），口头通过无效。
